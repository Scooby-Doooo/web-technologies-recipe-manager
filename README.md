# Recipe Manager

Лабораторні роботи з курсу «Web-технології». Усі етапи зроблені в одному проєкті —
застосунку для рецептів: рецепти з категоріями й інгредієнтами, фото, нотатки,
пошук, API і кілька інтеграцій навколо цього.

Задеплоєна версія: https://recipe-manager-iy74.onrender.com (безкоштовний сервер
засинає, тому перше відкриття може тривати до хвилини).

Стек: ASP.NET Core MVC на .NET 10, EF Core і PostgreSQL. Окремо є SPA на React
і MCP-сервер.

## Дані

Основні таблиці — `Category`, `Recipe`, `Ingredient` і `RecipeIngredient`. Остання
пов'язує рецепт з інгредієнтом «багато до багатьох» і зберігає кількість та одиницю.
Коли рецепт видаляють, його зв'язки з інгредієнтами видаляються каскадно, а категорію
чи інгредієнт, які ще десь використовуються, видалити не можна.

Пізніше додалися користувачі, кухні (`Tenant`), нотатки до рецептів і прив'язані
Telegram-чати. Схему створює міграція `InitialCreate`.

## Етапи

### Основа

**C1. MVC.** Для рецептів, категорій та інгредієнтів є звичайні сторінки Index,
Details, Create, Edit і Delete. Поля перевіряються атрибутами на сервері та jQuery
Validation у браузері, форми захищені antiforgery-токеном. До рецепта можна
завантажити фото (JPG, PNG або WEBP до 5 МБ). Файл отримує згенероване ім'я, а
старий видаляється лише після того, як нові дані збереглися в базі.

**C6. Landing page.** Сторінка рецепта зверстана на Bootstrap як лендинг: зверху
фото, назва, категорія, час і порції, нижче інгредієнти та інструкція. Блок з
контактами закріплений унизу екрана. Для рецептів без фото є окремий варіант верстки,
а на телефоні колонки стають одна під одною.

**C5. REST API.** API-контролери в `Controllers/Api` дублюють той самий CRUD через
JSON. Створення повертає 201 із заголовком `Location`, видалення — 204, помилки
приходять у форматі ProblemDetails. Для POST, PUT і DELETE потрібен токен з
`GET /api/antiforgery`. Скрипт `examples/c5-api-demo.ps1` проганяє весь CRUD
через curl і прибирає за собою.

**B1. Пагінація.** Якщо до списку в API додати `skip` або `limit`, приходить сторінка
`{ items, skip, limit, nextLink }`. Окремого COUNT немає: сервер бере на один запис
більше, ніж `limit`, і якщо він знайшовся, формує `nextLink`. Без параметрів API
повертає звичайний масив, як і раніше.

**B9. Кешування.** GET-запити API кешуються через Output Caching на 60 секунд.
Після кожного збереження перехоплювач EF Core викидає з кешу відповіді, яких
стосується зміна, тому правки з MVC-форм теж одразу видно в API.

### Інтерфейс

**F1. Статистика.** На сторінці `/Statistics` дві діаграми Chart.js: рецепти за
категоріями та за часом приготування. Дані рахуються одним запитом із групуванням,
під кожною діаграмою є таблиця з тими самими числами.

**F2. Autocomplete.** Категорію у формі рецепта обирають через Select2 з пошуком на
сервері. Запит іде від трьох символів, через 300 мс після останнього натискання, і
повертає по 20 результатів з довантаженням під час прокрутки. На тестовій базі з
мільйоном категорій відповідь займала приблизно 110–550 мс.

**C7. SEO.** На сторінках є meta description, canonical і Open Graph, форми закриті
від індексації. Сторінка рецепта містить JSON-LD `schema.org/Recipe`, а `robots.txt`
і `sitemap.xml` генеруються з бази. Lighthouse локально показав SEO 100 замість 90.

**C9. Google Analytics.** Підключено GA4 і дві свої події: `view_recipe` на сторінці
рецепта та `recipe_created` після створення. Друга передається через `TempData`, бо
після збереження форма перенаправляє на список.

**C15. File API.** Коли у формі обирають фото, скрипт показує прев'ю й розміри. Фото,
більше за 1 МБ або ширше за 1600 px, перемальовується на canvas у WEBP і підставляється
назад у поле через `DataTransfer`, тож на сервер іде вже менший файл.

**F6. Canvas.** Унизу сторінки рецепта можна зробити картинку для соцмереж: фото,
назва, час, порції та інгредієнти, квадрат 1080 × 1080 або Story 1080 × 1920, три теми.
Довга назва зменшується, поки не влізе, а зайві інгредієнти перетворюються на «+N more».
Картку можна зберегти як PNG.

### Нотатки

**C12. Markdown-редактор.** У рецепта є сторінка Notes з редактором блоками, як у
Notion. Скорочення на кшталт `## ` чи `- ` змінюють тип блоку, Enter і Backspace ділять
і зливають блоки, а блок без курсора показує відформатований Markdown.

**F3. Drag and drop.** Блоки можна перетягувати за ручку. Поки блок тягнуть, решта
розсувається, а на нові місця блоки з'їжджають з FLIP-анімацією. Стрілками ↑/↓ на ручці
блок переноситься і без миші.

**C13. Синхронізація.** Нотатки зберігаються на сервері в таблиці `RecipeNotes`, а
браузер надсилає через SignalR лише різницю з останньою версією: змінені блоки, видалені
блоки й порядок. Сервер накладає її і розсилає результат усім, у кого відкриті ці нотатки.
Поле `Version` слугує маркером паралельності, тож два одночасні збереження не затирають
одне одного. Правки, зроблені без зв'язку, надсилаються після повторного підключення.

**C14. Зміни в динаміці.** Коли приходить версія з іншого пристрою, нові блоки
проявляються, змінені спалахують жовтим, видалені на мить тьмяніють на старому місці, а
зсунуті пливуть на нові. Блок, у якому стоїть курсор на іншому пристрої, обведений
рамкою.

### Real-time

**C10. Polling, long polling, WebSocket.** Сторінка Live показує зміни рецептів кухні
чотирма способами: звичайний polling, adaptive polling, long polling і WebSocket.
Лічильники показують кількість запитів, порожніх відповідей і затримку. У моєму
вимірюванні в тиші polling витратив 21,9 КБ на одну подію, а WebSocket — 384 байти.

**C11. SignalR.** Те саме зроблено через хаб `KitchenHub`: кожне з'єднання потрапляє в
групу своєї кухні, а після перепідключення клієнт дотягує пропущені події методом
`Since`. Транспорт можна вибрати вручну. SignalR через WebSockets витратив 190 байт на
подію проти 124 у власного сокета з C10.

### Користувачі й кухні

**C16. Вхід через Google.** Дивитися рецепти може будь-хто, а змінювати — лише після
входу через Google (OAuth 2.0). Під час першого входу створюється локальний акаунт.
Для скриптів і MCP-сервера на сторінці акаунта можна отримати bearer-токен на 8 годин.

**B5. Кухні.** Кожен користувач отримує свою кухню, а приєднатися до чужої можна за кодом
запрошення. Ізоляцію роблять глобальні фільтри EF Core за `TenantId`, тому чужий рецепт
для запиту просто не існує, і відповідь — 404. Анонімні відвідувачі бачать публічну
демо-кухню.

**B6. Feature flags.** Кухня має план Free або Premium, а що відкриває план, задають
прапорці Microsoft.FeatureManagement зі своїм фільтром за планом. На Premium доступні
експорт рецептів у JSON і CSV та асистент, а на Free діє ліміт у 20 рецептів. План
перемикається на сторінці акаунта.

### Інтеграції

**C8. TheMealDB.** На сторінці Import можна шукати страви з TheMealDB за назвою,
категорією та інгредієнтом і імпортувати їх собі. Імпорт підбирає категорію й
інгредієнти з наявних, розбирає кількості на кшталт `1 1/2 tbsp` і не дає додати одну
страву двічі.

**C21. ШІ-асистент.** Сторінка Assistant — чат з моделлю DeepSeek через OpenRouter.
Відповідь приходить через Server-Sent Events, тому видно і міркування моделі, і виклики
інструментів. Інструментів п'ять: пошук, перегляд рецепта, категорії, статистика й
створення рецепта. Вони працюють через той самий `ApplicationDbContext`, тож асистент
бачить тільки рецепти своєї кухні.

**B2. Telegram-бот.** До бота @lab_recipe_manager_bot чат прив'язується одноразовим
кодом зі сторінки акаунта. Бот показує рецепти кухні (`/recipes`, `/recipe`, `/random`)
і пише про кожен новий рецепт. Локально він працює через long polling, на сервері —
через webhook.

**C22. MCP-сервер.** `src/RecipeManager.Mcp` — консольний MCP-сервер, який ШІ-агент
(наприклад, GitHub Copilot) запускає через stdio. Він ходить у REST API з C5 і має три
інструменти на читання та два на запис.

### Розгортання

**C4. Docker.** Образ збирається в кілька етапів, а запускається від непривілейованого
користувача. `compose.yaml` піднімає PostgreSQL, RabbitMQ і сам застосунок, дані лежать
у volumes. На порожній базі застосунок сам застосовує міграції.

**C2. Хмара.** Образ публікується на Docker Hub, а Render запускає його як безкоштовний
Web Service. Диск на Render не зберігається між деплоями, тому SQLite довелося замінити
на PostgreSQL у Supabase. Ключі Data Protection теж лежать у базі, щоб вхід не злітав
після деплою. Секрети задані змінними середовища на Render.

**C19. Фото в Supabase Storage.** На сервері фото зберігаються в bucket `recipe-photos`,
а браузер завантажує їх звідти напряму. Локально, без ключа Supabase, фото лягають у
`wwwroot/uploads`, як раніше. Щоб картку з F6 можна було зберегти, фото з іншого домену
вантажиться з CORS.

### Пізніші етапи

**B4. Пошук.** `GET /api/recipes/search?q=…` шукає рецепти через Lucene.NET по назві,
інгредієнтах, категорії, опису й інструкції. Збіг у назві важить більше, а слова
зводяться до основи, тому `tomatoes` знаходить «Tomato soup». Працює синтаксис Lucene
(`OR`, `garl*`, `title:soup`) і фільтр `maxMinutes`. Індекс тримається в пам'яті й
перебудовується для кухні після змін у ній.

**B8. RabbitMQ.** Повідомлення в Telegram про нові рецепти йдуть через RabbitMQ (на
сервері — CloudAMQP). Якщо Telegram не відповів, повідомлення чекає в черзі повтору й
повертається назад, а після п'яти невдач лягає в окрему чергу `failed`. Без адреси
брокера використовується звичайна черга в пам'яті.

**F5. SPA.** `src/RecipeManager.Spa` — окремий проєкт на React і Vite, який працює лише
через JSON API: список з пагінацією, пошук з B4, сторінка рецепта, створення й
редагування з фото. Збірка лежить на тому самому сайті під `/spa`, тому вхід через
Google працює без окремих налаштувань.

### Тестування

**QA1.** У `tests/postman` є колекції Postman, які запускаються через Newman. Основна
колекція перевіряє CRUD, валідацію, фото й захист від CSRF, а потім повертає дані до
початкового стану: 75 запитів і 299 перевірок. Ще дві колекції окремо перевіряють
пагінацію (B1) і кеш (B9).

**QA2.** E2E-тести в `tests/e2e` написані на Playwright і запускаються в Chrome. Кожен
прогін піднімає свій сервер з окремою базою в Docker, тому робоча база не змінюється.
Зараз тестів 71, з них бенчмарк із C10 за замовчуванням пропускається. Скрипт
`coverage.js` додатково рахує, скільки з 25 MVC-маршрутів реально відкривалися в тестах.

**QA3.** 17 тестів перевіряють автентифікацію й доступ: матрицю з 58 адрес, open
redirect, прапорці cookie, CSRF, підроблені та прострочені токени й ізоляцію кухонь.
Одна знайдена проблема лишилася: вихід не відкликає скопійований раніше cookie.

## Як запустити

Потрібні .NET 10 SDK, Node.js 22 і Docker Desktop.

```
docker compose up -d db
cd src/RecipeManager.Spa && npm ci --ignore-scripts && npm run build && cd ../..
dotnet tool restore
dotnet ef database update --project src/RecipeManager.Web
dotnet run --project src/RecipeManager.Web --launch-profile http
```

Сайт відкриється на http://localhost:5105. База запускається в Docker на порту 5433.
Ключі Google, Telegram і OpenRouter у репозиторій не потрапляють, їх треба покласти в
user secrets (`dotnet user-secrets set ... --project src/RecipeManager.Web`). Без них
застосунок теж працює, просто без входу, бота й асистента.

Усе разом у Docker (сайт на http://localhost:8080):

```
docker compose up --build -d
```

Тести:

```
cd tests/e2e && npm ci --ignore-scripts && npm test
cd tests/postman && npm ci --ignore-scripts && npm test
```

E2E-тести самі запускають сервер і бази, але перед ними треба зібрати SPA. Для Postman
застосунок потрібно запустити окремо: з тестовим входом, на окремій базі й без
Telegram-бота, щоб не чіпати свої дані та справжнього бота:

```
dotnet ef database update --project src/RecipeManager.Web --connection "Host=localhost;Port=5433;Database=qa1;Username=recipe_manager;Password=recipe_manager"
dotnet run --project src/RecipeManager.Web --no-launch-profile -- --urls http://localhost:5105 --environment Development --ConnectionStrings:DefaultConnection "Host=localhost;Port=5433;Database=qa1;Username=recipe_manager;Password=recipe_manager" --Authentication:EnableTestSignIn true --Telegram:BotToken ""
```

## Структура

- `src/RecipeManager.Web` — сам застосунок;
- `src/RecipeManager.Spa` — SPA на React (F5);
- `src/RecipeManager.Mcp` — MCP-сервер (C22);
- `tests/postman` і `tests/e2e` — тести;
- `examples` — демо API через curl.
