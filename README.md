# Лабораторні роботи з курсу «Web-технології»

**Тема проєкту: Recipe Manager — вебзастосунок для збереження рецептів**

Застосунок: ASP.NET Core MVC (.NET 10) · БД: PostgreSQL через Entity Framework Core

Сайт: https://recipe-manager-iy74.onrender.com

## Про застосунок

Усі етапи курсу виконуються в одному проєкті. Застосунок зберігає рецепти,
розкладені за категоріями, і довідник інгредієнтів. Для рецепта вказуються
опис, інструкція, час приготування, кількість порцій і, за бажанням, фото.
Кожен рецепт має власну сторінку-лендинг. Ті самі дані доступні через JSON API,
а на окремій сторінці показано статистику у вигляді діаграм.

## Модель даних

Чотири таблиці:

- `Category` — категорія (Breakfast, Dessert тощо), один до багатьох із `Recipe`;
- `Recipe` — рецепт; поле `ImagePath` зберігає посилання на завантажене фото;
- `Ingredient` — довідник інгредієнтів;
- `RecipeIngredient` — зв'язок «багато до багатьох» між рецептом та інгредієнтом
  з кількістю й одиницею виміру, первинний ключ `(RecipeId, IngredientId)`.

Під час видалення рецепта його зв'язки з інгредієнтами видаляються каскадно.
Категорію чи інгредієнт, які ще використовуються, видалити не можна.
Схема й початкові довідники створюються міграцією `InitialCreate`.

## Як це працює

**C1. MVC.** Для кожної сутності є контролер і стандартні сторінки Index,
Details, Create, Edit, Delete. Перевірка полів зроблена атрибутами
DataAnnotations на сервері й jQuery Validation у браузері, POST-форми захищені
antiforgery-токеном. Фото зберігається під згенерованим ім'ям у
`wwwroot/uploads/recipes` або, на сайті, в Supabase Storage (C19), а в БД записується
лише посилання на нього. Під час заміни фото або видалення рецепта старий файл
прибирається вже після успішного збереження в БД.

**C6. Landing Page.** Сторінка рецепта зібрана на Bootstrap: у першому блоці фото,
а поруч назва, категорія, час і кількість порцій; нижче інгредієнти та
покрокова інструкція.
Блок з контактами закріплений унизу екрана. На телефоні колонки стають
одна під одною, а для рецептів без фото є окремий варіант верстки.

**C12. Нотатки.** Сторінка Notes рецепта — редактор, у якому документ є списком блоків з
`id`, типом і текстом у Markdown. Скорочення на кшталт `## ` чи `- ` змінюють тип блоку,
Enter і Backspace розбивають і зливають блоки, а блок без курсора показує відформатований
`**жирний**`, `*курсив*`, код і посилання. Документ зберігається в `localStorage` через
300 мс після зміни й відновлюється після перезапуску браузера.

**F3. Перетягування блоків.** У кожного блоку нотаток є ручка, за яку його можна перетягнути
(HTML Drag and Drop API). Поки блок тягнуть, інші блоки розсуваються під курсором і
з'їжджають на нові місця з анімацією FLIP через `element.animate`. Після відпускання
нумерація оновлюється, а порядок зберігається в `localStorage`. Стрілки ↑ / ↓ на ручці
переносять блок без миші.

**C13. Синхронізація нотаток.** Нотатки зберігаються в таблиці `RecipeNotes`. Браузер надсилає
в `KitchenHub` лише зміну відносно останньої отриманої версії: нові й змінені блоки,
видалені `id` і новий порядок. Сервер накладає її на документ і розсилає результат усім, у
кого ці нотатки відкриті, а кожен браузер кладе свої ще не надіслані правки поверх. Поле
`Version` — маркер паралельності EF Core, тому два одночасні збереження не затирають одне
одного.

**C14. Показ змін у динаміці.** Отримавши документ з іншого пристрою, редактор порівнює
блоки до і після за `id`. Нові блоки проявляються, змінені спалахують жовтим, для
видалених на старому місці на мить лишається копія, яка тьмяніє, а всі зсунуті блоки
пливуть на нові місця тим самим FLIP, що й у F3. Окремий метод хаба `FocusNotes` передає
іншим копіям, у якому блоці стоїть курсор, і цей блок отримує рамку «Another device is here».

**C2. Хмара.** Docker-образ з C4 збирається під `linux/amd64` і публікується на
Docker Hub, а безкоштовний Web Service на Render запускає його з цього образу. Диск
контейнера на Render не зберігається між деплоями, тому застосунок перейшов із SQLite
на PostgreSQL: у хмарі це база Supabase, локально — сервіс `db` з `compose.yaml`.
Ключі Data Protection теж лежать у базі, тож вхід переживає деплой. Секрети задано
змінними середовища на Render, а Data API Supabase закрито, щоб таблиці не були
доступні за публічним ключем.

**C19. Фото в Storage.** Збереження фото винесено в сервіс `IPhotoStorage`. Якщо задано
адресу й секретний ключ Supabase, фото надсилаються в публічний bucket `recipe-photos`,
а рецепт зберігає їхню публічну адресу; без них фото, як і раніше, лягають у
`wwwroot/uploads`. Браузер завантажує фото прямо із Supabase, ключ лишається на сервері,
а картка F6 вантажить фото з `crossOrigin`, щоб canvas можна було експортувати.

**B4. Пошук.** `GET /api/recipes/search?q=…` шукає рецепти через Lucene.NET. Кожен рецепт —
документ із назвою, інгредієнтами, категорією, описом та інструкцією; збіг у назві важить
більше, а `EnglishAnalyzer` зводить слова до основи, тож `tomatoes` знаходить «Tomato soup».
Підтримується синтаксис Lucene (`OR`, `garl*`, `title:soup`) і фільтр `maxMinutes`. Індекс
лежить у пам'яті: перехоплювач `SaveChanges` позначає кухню після кожної зміни, і наступний
пошук перебудовує її документи з бази.

**B8. RabbitMQ.** Після створення рецепта подія `recipe.created` публікується в RabbitMQ
з підтвердженням від брокера, а фоновий споживач надсилає з неї оголошення в Telegram і
підтверджує повідомлення лише після успіху. Якщо Telegram не відповів, повідомлення через
dead-letter потрапляє в чергу повтору з TTL і повертається назад; після кількох невдач
воно лягає в окрему чергу `failed`. Без адреси брокера використовується черга в пам'яті.

**F5. SPA.** `src/RecipeManager.Spa` — окремий проєкт на React 19 з React Router і Vite,
який працює з сервером лише через JSON API: сторінки списку з B1, пошук з B4, CRUD і
завантаження фото з C5. Збірка лягає у `wwwroot/spa`, і застосунок роздає її під `/spa`
з того самого origin, тож SPA використовує звичайний вхід через Google й antiforgery-токен
без CORS. Для глибоких посилань сервер повертає `index.html`, а маршрут розбирає React Router.

**C11. SignalR.** `KitchenHub` додає кожне з'єднання до групи його кухні, а перехоплювач
з C10 після збереження надсилає зміну цій групі. Після підключення й повторного
з'єднання клієнт викликає метод хаба `Since` і отримує пропущені події. На сторінці Live
SignalR можна запустити з автоматичним вибором транспорту або примусово через WebSockets,
SSE чи long polling. У вимірюванні SignalR через WebSockets витрачає 190 байт на подію
проти 124 у власного сокета з C10.

**C10. Live.** Перехоплювач EF Core передає кожну зміну рецепта в стрічку кухні в пам'яті.
Сторінка Live отримує її звичайним polling щосекунди, adaptive polling (1–16 с), long
polling або через WebSocket, а лічильники на сторінці показують запити, порожні відповіді,
дані й затримку. Окремий вимірювальний тест рахує байти разом із заголовками: у тиші
polling витратив 21,9 КБ на одну подію, WebSocket — 384 байти.

**C8. TheMealDB.** Сторінка Import шукає страви у відкритому API TheMealDB під час
введення і фільтрує їх за категорією та основним інгредієнтом. Запити йдуть через
`ImportController`, який кешує відповіді й поєднує два фільтри перетином. Імпорт
зіставляє категорію й інгредієнти з наявними в кухні, розбирає кількості на кшталт
`1 1/2 tbsp` і завантажує фото лише з хоста TheMealDB. Колонка `MealDbId` з
унікальним індексом не дає імпортувати страву двічі.

**F6. Картка рецепта.** Унизу сторінки рецепта `recipe-card.js` малює на canvas
картинку для соцмереж: фото, категорію, назву, час, порції й інгредієнти. Можна
вибрати квадрат 1080 × 1080 або Story 1080 × 1920 і одну з трьох тем. Назва
зменшується, поки не влізе у відведені рядки, а зайві інгредієнти стають «+N more».
Кнопка Download PNG зберігає картку через `canvas.toBlob`.

**C15. File API.** Коли у формі рецепта вибирають фото, скрипт
`image-upload.js` читає `File` з поля, перевіряє тип і декодує картинку через Blob URL.
Фото більше 1 МБ або ширше за 1600 px перемальовується на canvas, кодується в WEBP
і кладеться назад у поле через `DataTransfer`, тож форма відправляє вже менший файл.
Під полем видно прев'ю, розміри в пікселях і розмір до та після стиснення. Серверна
перевірка з C1 не змінилася.

**C7. SEO.** У `<head>` кожної сторінки додано meta description, canonical,
robots і теги Open Graph, а форми закрито від індексації. Сторінка рецепта
містить JSON-LD `schema.org/Recipe` з інгредієнтами, кроками й часом
приготування. `robots.txt` і `sitemap.xml` генеруються з БД. Локальний аудит
Lighthouse показав зростання SEO з 90 до 100. Аудит у Seobility буде після
розгортання сайту.

**C16. Вхід через Google.** Переглядати рецепти може будь-хто, а створювати,
редагувати й видаляти — лише після входу через Google (OAuth 2.0, бібліотека
`Microsoft.AspNetCore.Authentication.Google`). Під час першого входу в таблиці
`Users` створюється локальний акаунт; користувача шукають за ID Google, а не за
email. Браузер отримує cookie, а для скриптів і MCP-сервера на сторінці акаунта
можна створити bearer-токен на 8 годин. Без входу API на запис відповідає `401`.
Client ID і секрет зберігаються в user secrets, не в репозиторії.

**B5. Тенанти.** Тенант — це кухня. Рецепти, категорії та інгредієнти належать
одній кухні, і її учасники не бачать даних інших кухонь. Ізоляцію забезпечують
глобальні фільтри EF Core за `TenantId`, тож фільтр діє на всі запити без окремих
перевірок у контролерах: чужий рецепт для запиту просто не існує, і відповідь — `404`.
Під час збереження нові рядки автоматично отримують кухню користувача. Кожен новий
користувач отримує власну кухню, іншу можна приєднати за кодом запрошення. Анонімні
відвідувачі бачать публічну демо-кухню, тому лендинги й SEO працюють як раніше.

**B6. Feature flags.** Кожна кухня має план Free або Premium. Що відкриває план,
задають прапорці Microsoft.FeatureManagement в `appsettings.json`, а власний фільтр
`Plan` вмикає прапорець за планом кухні з БД. Прапорець `RecipeExport` відкриває
Premium-сторінку експорту рецептів у JSON і CSV (`[FeatureGate]`, на Free — сторінка
«Premium feature» з кодом `403`). `UnlimitedRecipes` знімає ліміт 20 рецептів, який на
Free перевіряється і у формі, і в API. План перемикається на сторінці акаунта.

**QA3. Тести автентифікації.** 17 Playwright-сценаріїв перевіряють вхід, токени й
доступ. Матриця доступу проходить 58 адрес: усі дії, що змінюють дані, для аноніма
мають перенаправляти на вхід чи давати `401`, а публічні сторінки — відкриватися.
Окремо перевіряються open redirect у `returnUrl`, прапорці cookie й підроблений cookie,
CSRF для дій акаунта, підроблені та прострочені bearer-токени, відсутність тестового
входу в Production, ізоляція кухонь і доступ за планом. У звіті описано й знайдені
обмеження: наприклад, вихід не відкликає скопійований cookie.

**C21. ШІ-агент.** Сторінка Assistant — чат з моделлю `deepseek/deepseek-v4.1-flash-1017`
через OpenRouter. Сервер повертає відповідь як Server-Sent Events: окремими подіями йдуть
міркування моделі, виклики інструментів з аргументами, їхні результати й текст відповіді,
а сторінка показує все це одразу. Агент має 5 інструментів: пошук, перегляд рецепта,
категорії, статистика й створення рецепта. Вони працюють через `ApplicationDbContext`,
тож фільтр кухні і правила форми діють і для моделі. Асистент — Premium-функція.

**B2. Telegram-бот.** Чат прив'язується до кухні одноразовим кодом зі сторінки акаунта
(посилання `t.me/<бот>?start=<код>`). Бот показує рецепти кухні (`/recipes`, `/recipe`,
`/random`) і повідомляє про кожен новий рецепт: їх ловить перехоплювач `SaveChanges`,
тож неважливо, звідки рецепт прийшов. Локально бот отримує повідомлення через long
polling, після розгортання — через webhook із секретним заголовком. Клієнт Bot API
написаний на `HttpClient` без бібліотеки й не пише токен у лог.

**C9. Google Analytics.** Layout підключає тег `gtag.js` з Measurement ID
з `appsettings.json`. Окрім стандартного `page_view`, надсилаються дві кастомні
події: `view_recipe` (ID, категорія й час рецепта) на сторінці рецепта і
`recipe_created` після створення рецепта через форму. Друга подія передається
через `TempData`, бо після збереження відбувається redirect на список.

**C4. Docker.** Образ збирається у два етапи: SDK для `dotnet publish` і легкий
runtime-образ для запуску від непривілейованого користувача. `compose.yaml`
піднімає PostgreSQL, RabbitMQ (B8) і застосунок, який чекає їхньої готовності.
Volumes зберігають файли бази, брокера та фото, тож дані переживають перестворення
контейнерів. На порожній базі застосунок сам застосовує міграції під час старту.

**C5. REST API.** Окремі API-контролери в `Controllers/Api` повертають і
приймають JSON. Створення дає 201 із заголовком `Location`, видалення — 204,
помилки — 400, 404, 409 або 415 у форматі ProblemDetails. Для POST, PUT і DELETE
потрібен antiforgery-токен, який видає `GET /api/antiforgery`. Сценарій
`examples/c5-api-demo.ps1` проходить увесь CRUD через curl і після себе
видаляє створені записи.

**QA1.** У `tests/postman` лежить колекція Postman (формат v2.1) і локальне
середовище. Колекція створює власні записи, перевіряє коди відповідей, валідацію,
завантаження фото, захист від CSRF і наприкінці порівнює дані з початковими.
Запуск з термінала — через Newman (`npm test`), повний прохід дає 75 запитів
та 299 перевірок.

**B1. Pagination.** Якщо до запиту списку додати `skip` або `limit`, API
повертає сторінку `{ items, skip, limit, nextLink }`. Щоб не робити окремий
COUNT, сервер читає на один запис більше, ніж `limit`: якщо він є, формується
`nextLink`. Без цих параметрів API, як і в C5, повертає звичайний масив.
Для пагінації є окрема Postman-колекція (`npm run test:pagination`).

**B9. Кешування.** GET-запити API кешуються в пам'яті через Output Caching
на 60 секунд. EF Core interceptor після кожного успішного збереження видаляє з
кешу відповіді, яких стосується зміна. Тому і зміни через API, і зміни через
MVC-форми одразу видно в API. Окрема Postman-колекція (`npm run test:caching`)
перевіряє влучання в кеш за заголовком `Age` і очищення після змін.

**F1. Статистика.** `StatisticsController` одним запитом групує рецепти за
категорією та діапазоном часу приготування. Chart.js будує з цього дві діаграми,
під кожною є таблиця з тими самими числами.

**F2. Autocomplete.** Звичайний випадний список категорій замінено на Select2.
Запит на сервер іде від 3 символів, через 300 мс після останнього натискання.
Сервер шукає підрядок у назві й віддає по 20 результатів, наступні
підвантажуються під час прокрутки. Перевірка на окремій БД з 1 000 000 категорій
показала час відповіді приблизно від 110 до 550 мс.

**C22. MCP сервер.** `src/RecipeManager.Mcp` — консольний MCP-сервер на
офіційному C# SDK, який агент (наприклад, GitHub Copilot) запускає через stdio. Він
працює через REST API з C5, а не напряму з БД. Інструменти `list_categories`,
`search_recipes`, `get_recipe` читають дані, а `create_category` і
`create_recipe` створюють нові записи. Помилки валідації API повертаються агенту
текстом, щоб він міг виправити запит.

**QA2. E2E.** Тести в `tests/e2e` написані на Playwright і запускаються в Chrome.
Для кожного прогону створюється тимчасова БД через ті самі міграції, і сервер
стартує на окремому порту, тож робоча база не змінюється. Набір містить
59 сценаріїв. Окремо рахується, скільки з 25 MVC-маршрутів реально відкривалися
в тестах. Це покриття сценаріїв і маршрутів, а не рядків коду.

## Запуск

Потрібні .NET 10 SDK, Node.js 22 (для SPA) і Docker Desktop (для бази PostgreSQL). З кореня
репозиторію:

```
docker compose up -d db
cd src/RecipeManager.Spa && npm ci --ignore-scripts && npm run build && cd ../..
dotnet restore
dotnet tool restore
dotnet ef database update --project src/RecipeManager.Web
dotnet run --project src/RecipeManager.Web --launch-profile http
```

Застосунок відкривається на http://localhost:5105. Для входу через Google
потрібно один раз зберегти Client ID і секрет OAuth-клієнта в user secrets.

Або повністю в Docker, застосунок буде на http://localhost:8080:

```
docker compose up --build -d
```

Рядок підключення задано в `src/RecipeManager.Web/appsettings.json`: база
`recipe_manager` у контейнері `db` на порту 5433.

Тести (потрібен Node.js; для E2E ще й Google Chrome і Docker):

```
cd tests/postman && npm ci --ignore-scripts && npm test
cd tests/e2e && npm ci --ignore-scripts && npm test
```

Перед запуском Postman-колекції застосунок треба запустити на окремій тестовій
БД. E2E-тести
піднімають сервер самі.

## Структура репозиторію

- `src/RecipeManager.Web` — застосунок (контролери, моделі, Razor-сторінки, міграції);
- `src/RecipeManager.Mcp` — MCP-сервер (C22);
- `src/RecipeManager.Spa` — SPA на React (F5);
- `examples` — скрипт демонстрації API через curl;
- `tests/postman` — тести API (QA1, B1, B9);
- `tests/e2e` — E2E-тести (QA2).
